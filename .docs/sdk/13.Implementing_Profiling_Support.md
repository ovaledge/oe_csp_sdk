# 13. Implementing Profiling Support (Optional)

Profiling is an **optional** connector capability: table/column statistics (row counts, min/max, distinct/null/empty/zero counts, top values, patterns) computed for a catalog object. Nothing here is required to ship a connector — skip this page entirely if your connector only needs connection validation, metadata crawl, and sample data preview.

This page is the **hands-on walkthrough**: generate the scaffold, implement the SPI, wire it up, test it, and ship it. It intentionally does not repeat the full method/field contract — that lives in one place:

* **SPI contract, field mapping, identity rules, exceptions, batch modes, gaps vs. legacy:** [Connector Interface Reference §4.4](../Connector_Interface_Reference.md#44-profilingservice-optional-contract) — treat that section as the source of truth if anything here seems to disagree with it.
* **Where profiling sits in overall SDK scope:** [05. What you will develop §5.6](05.What_you_will_develop.md#56-sdk-scope-and-limitations).

---

## 13.1 Decide what to implement

| Choice | When to pick it | What you implement |
|---|---|---|
| **Off (default)** | Your source has no meaningful row/column statistics, or you're not ready to invest the effort yet. | Nothing. Don't override `getProfilingService()`; leave `profiling`/`sampleProfiling` `false` in the connector JSON. |
| **Sample-only** | Non-JDBC / API-style connectors (Apps) that can page through rows for a crawled `ENTITY` but can't cheaply run server-side aggregates (`MIN`/`MAX`/`COUNT DISTINCT`, etc.). | `getRowCount` + `sampleProfile`. Leave `profileColumn` un-overridden (base throws `ProfilingUnsupportedException`, which is correct). |
| **Full DBMS** | JDBC/SQL sources where the database can compute aggregates efficiently. | `getRowCount` + `profileColumn` + `sampleProfile`, using `JdbcProfilingSqlUtils` for dialect SQL. |
| **File** | Connector exposes `FILE` objects (CSV/Excel-like) that should be profiled by parsing content. | `profileFile` in addition to whichever of the above applies to your other object kinds. |

Profiling only applies to `ObjectKind.ENTITY` / `VIEW` (tabular) and `ObjectKind.FILE`. Every other kind (`REPORT`, `DASHBOARD`, `FUNCTION`, `PROCEDURE`, `DATASET`, `FILEFOLDERS`, etc.) must be rejected — see [13.5.1](#1351-kind-and-identity-rules).

---

## 13.2 Prerequisites

* You've already completed [05](05.What_you_will_develop.md)–[07](07.Development_And_Testing.md): the connector implements `AppsConnector` + `MetadataService` + `QueryService`, and `getContainers()/getObjects()/getFields()` work.
* You know which `ObjectKind`s your connector declares in `getSupportedObjects()` — profiling methods are generated per kind, so pick `ENTITY`/`VIEW`/`FILE` deliberately before generating.
* `csp-sdk-core` on the classpath (already a dependency of every connector module) supplies the SPI: `ProfilingService`, `AbstractProfilingService`, the request/response models, `ProfilingException`/`ProfilingUnsupportedException`, and the helper utilities `JdbcProfilingSqlUtils`, `ProfileStatsCalculator`, `ProfilingConstants`.

---

## 13.3 Step 1 — Generate the scaffold

**Use the csp-api UI generator (Section A of [06](06.Generate_the_new_Connector_Source.md)).** The Maven archetype CLI (Section B) technically has the same template placeholders, but they default to empty and generating a working profiling stub from the CLI means hand-supplying fully-formed Java source as archetype properties — not a realistic workflow. Partners should always go through the UI generator.

1. Open `http://localhost:8800/` → **Create New Connector**.
2. Fill in Basic Info and pick a **Protocol** (`JDBC` if you want the DBMS mode available).
3. Under **Connector Capabilities → Core Capabilities**, check **Profiling**. A **Mode** toggle appears:
   * **Sample only** (default) — generates `getRowCount` + `sampleProfile` stubs.
   * **Auto + Sample** (DBMS) — generates `getRowCount` + `profileColumn` + `sampleProfile` stubs. Only meaningful for `JDBC` protocol or when `FILE` is one of your object kinds.
4. Under **Supported Objects**, select `ENTITY`/`VIEW` for tabular profiling and/or `FILE` for file profiling. Profiling methods are only generated for the kinds you pick here — pick none of these and checking Profiling has no effect on the generated code (only the JSON flags/crawler options change).
5. Under **Crawler Options**, note that checking Profiling force-enables crawler preference **`P` (PROFILE)** and reveals **`PROFILE_OPTIONS`** / **`PROFILE_TYPES`**. You don't need to hand-pick `PROFILE_TYPES`; the generator constrains the allow-list to what your mode supports (see [13.4](#134-what-gets-generated)).
6. Choose **Download** or **Publish** as usual and follow the remaining steps in [06](06.Generate_the_new_Connector_Source.md).

If you're **retrofitting an existing connector** (generated before you decided to add profiling), there's no "re-run generator on existing module" flow — add the file by hand using the shape in [13.4](#134-what-gets-generated) below, plus the connector wiring in [13.6](#136-step-3--wire-it-into-the-connector) and the JSON flags in [13.7](#137-step-4--declare-capability-in-connector-json).

## 13.4 What gets generated

With Profiling checked, the generator produces (in addition to the usual `Connector`/`MetadataService`/`QueryService` files):

* `{Prefix}ProfilingService.java` — extends `AbstractProfilingService`, with one `@Override` stub per applicable method, plus a generated `validateIdentity(ConnectionConfig, containerId, entityId)` private helper (null/blank checks that throw `ProfilingException`). **`validateIdentity` is not an SDK method** — it's boilerplate the generator writes into your class (the reference `MonetDBProfilingService` defines its own copy the same way). If you're hand-writing a `ProfilingService` instead of generating one, add an equivalent helper yourself.
* A unit test scaffold: `{Prefix}ProfilingServiceUnitTest.java`.
* Connector wiring: a `profilingService` field, `getProfilingService()` override, and imports in `{Prefix}Connector.java`.
* A `getProfilingService_returnsProfilingServiceInstance()` test appended to `{Prefix}ConnectorUnitTest.java`.
* Connector JSON capability flags and crawler options (see [13.7](#137-step-4--declare-capability-in-connector-json)).

**Sample-only mode** generates (for `ENTITY`/`VIEW`):

```java
@Override
public List<String> getSkipDataTypesForProfile() {
    // TODO: return types to soft-skip during sample profiling if applicable.
    return Collections.emptyList();
}

@Override
public long getRowCount(ProfileRowCountRequest request) {
    requireObjectKind(request, ObjectKind.ENTITY, ObjectKind.VIEW);
    validateIdentity(request.getConnectionConfig(), request.getContainerId(), request.getEntityId());
    // Required for SAMPLE: OvalEdge calls getRowCount before sampleProfile and skips the
    // object on ProfilingUnsupportedException or a zero count. Honor rowCountLimit when set.
    // TODO: count source records for this entity (do not return 0 when data exists).
    return 0L;
}

@Override
public Map<String, ProfileColumnResult> sampleProfile(SampleProfileRequest request) {
    requireObjectKind(request, ObjectKind.ENTITY, ObjectKind.VIEW);
    validateIdentity(request.getConnectionConfig(), request.getContainerId(), request.getEntityId());
    // TODO: fetch sample data for the object and compute ProfileColumnResult per field
    // using ProfileStatsCalculator (or connector-specific sample logic for non-JDBC sources).
    return new LinkedHashMap<>();
}
```

Note `profileColumn` is **not** generated in Sample-only mode — the base class's default (throw `ProfilingUnsupportedException`) is the correct behavior; don't override it unless you actually can compute server-side aggregates.

**DBMS mode** additionally generates `profileColumn`:

```java
@Override
public ProfileColumnResult profileColumn(ProfileColumnRequest request) {
    requireObjectKind(request, ObjectKind.ENTITY, ObjectKind.VIEW);
    validateIdentity(request.getConnectionConfig(), request.getContainerId(), request.getEntityId());
    // TODO: implement aggregate column profiling (JdbcProfilingSqlUtils + soft-skip / null-count paths).
    ProfileColumnResult result = new ProfileColumnResult();
    result.setMessage("TODO: implement profileColumn");
    return result;
}
```

If `FILE` is one of your selected object kinds (either mode), this is also generated:

```java
@Override
public FileProfileResponse profileFile(FileProfileRequest request) {
    requireObjectKind(request, ObjectKind.FILE);
    validateIdentity(request.getConnectionConfig(), request.getContainerId(), request.getEntityId());
    // TODO: implement legacy FilesDtoInterface.profileFile parity
    // (parse + column stats mapping into FileProfileResponse).
    return new FileProfileResponse();
}
```

Connector wiring (`{Prefix}Connector.java`):

```java
private final {Prefix}ProfilingService profilingService = new {Prefix}ProfilingService();

@Override
public ProfilingService getProfilingService() {
    return profilingService;
}
```

None of these stubs perform real profiling yet — every `TODO` needs real logic before you can declare the capability truthfully. Treat the generated file the same way you treat the generated `MetadataService`/`QueryService`: a compilable starting point, not a finished implementation.

## 13.5 Step 2 — Implement the SPI methods

Extend `AbstractProfilingService` (already done by the generator) instead of implementing `ProfilingService` directly — it gives you:

* `requireObjectKind(request, ObjectKind...)` — throws `ProfilingUnsupportedException("Unsupported profiling objectKind")` when the request's `objectKind` is `null` or not in the allow-list you pass. **Call this first** in every method you override.
* Correct **default behavior for everything you don't override**: `getRowCount`, `profileColumn`, `sampleProfile`, and `profileFile` each throw `ProfilingUnsupportedException("<method> is not supported by this connector")` out of the box. `getSkipDataTypesForProfile()` defaults to an empty list. This is why Sample-only connectors can safely skip `profileColumn` entirely.
* `resetBatchExceptionStreak()` and the batch methods (`getRowCountBatch`, `profileColumnBatch`, `sampleProfileBatch`, `profileBatch`) are already implemented as default loops over your single-item methods, with an unhandled-exception streak guard. Override a batch method only if you need to send one remote payload instead of looping (e.g., a Bridge-backed connector) — see [Connector Interface Reference §4.4](../Connector_Interface_Reference.md#44-profilingservice-optional-contract) for the batch mode table.

### 13.5.1 Kind and identity rules

Every profiling request identifies its target the same way as metadata/query requests, plus an `objectKind`:

| Object type | `objectKind` | `containerId` | `entityId` | `fieldName` |
|---|---|---|---|---|
| DBMS table/view | `ENTITY` or `VIEW` | schema | table/view name | column (column profile only) |
| Apps sample-only object | `ENTITY` | container id from `getContainers()` | object id from `getObjects()` | field key from `getFields()` |
| File | `FILE` | folder/bucket prefix (if applicable) | file name / `extRefId` | n/a (`FileProfileRequest` carries `location`, `sheetName`, `hasHeaders`, etc. instead) |

For any other kind, throw `ProfilingUnsupportedException` (or simply don't override the method — `requireObjectKind` does this for you as long as you pass the correct allow-list).

### 13.5.2 Worked example — full DBMS (`monetdb`)

`monetdb` in this repo (`monetdb/src/main/java/com/ovaledge/csp/apps/monetdb/main/MonetDBProfilingService.java`) is the reference implementation for full DBMS profiling. Pattern to follow:

```java
@Override
public long getRowCount(ProfileRowCountRequest request) {
    requireObjectKind(request, ObjectKind.ENTITY, ObjectKind.VIEW);
    validateIdentity(request.getConnectionConfig(), request.getContainerId(), request.getEntityId());
    ConnectionConfig config = MonetDBConnector.ensureConnectionConfig(request.getConnectionConfig());
    ConnectionResource resource = obtainJdbcResource(config); // your pooled JDBC accessor
    String sql = JdbcProfilingSqlUtils.buildRowCountSql(
            request.getContainerId(), request.getEntityId(), request.getAdvancedDataQuery());
    Long count = resource.queryForObject(sql, "profileRowCount", (rs, i) -> rs.getLong(1));
    return count != null ? count : 0L;
}
```

`profileColumn` in the reference implementation: check `isSkippedDataType` / `exceedsMaxLength` first and return a **soft-skip result** (don't throw) when the type/length isn't supported; otherwise run `JdbcProfilingSqlUtils.buildAggregateProfileSql(...)` and map the single result row into `ProfileColumnResult`.

`sampleProfile` pages through rows (`JdbcProfilingSqlUtils.buildSampleSql`) and calls `ProfileStatsCalculator.rearrangeRowToColumnData` + `computeStatsForColumn` + `mergeSamplePage` per page — this calculator is the single source of truth for sample statistics; don't reimplement the math in the connector.

Helper utilities available from `csp-sdk-core` (don't reinvent these):

| Class | What it gives you |
|---|---|
| `JdbcProfilingSqlUtils` | `buildRowCountSql`, `buildAggregateProfileSql`, `buildSampleSql`, `buildTopValuesSql`, `buildNonNullCountSql`, `quoteIdentifier`, `isSkippedDataType`, `exceedsMaxLength`, `isStringDataType`, `isNumericDataType`, `appendAdvancedClause`/`validateAdvancedClause` (for `advancedDataQuery`/`advancedSampleClause`). |
| `ProfileStatsCalculator` | `computeStatsForColumn`, `computeStatsForFileColumn`, `mergeSamplePage`, `mergePageStats`, `rearrangeRowToColumnData`, `getPattern`/`validatePattern`, `sortTop50Values`. |
| `ProfilingConstants` | Default limits (`DEFAULT_SAMPLE_PAGE_SIZE = 1000`, `DEFAULT_TOP_VALUES_LIMIT = 50`, `DEFAULT_MAX_COLUMN_PROFILE_LENGTH = 4000`, `DEFAULT_BATCH_UNHANDLED_EXCEPTION_THRESHOLD = 10`), status codes (`PROFILE_STATUS_SAMPLE_FALLBACK = 1`, `PROFILE_STATUS_NULL_COUNT = 4`), and skip-message helpers (`skipDatatypeMessage`, `skipLengthMessage`, `withSkipExceptNullCount`). |

Dialect-specific SQL (identifier quoting rules, unsupported types, etc.) stays in your connector — only the SQL *shape* is shared.

### 13.5.3 Soft skips vs. hard failures

* **Soft skip** (unsupported datatype, oversized column, etc.): return a `ProfileColumnResult` with `unsupportedDataTypeForProfile` set (datatype skip only) and a message from `ProfilingConstants`. **Do not throw.** Still populate `notNullCount` if you can cheaply compute it.
* **Unsupported operation/kind**: throw `ProfilingUnsupportedException`. The csp-api controller maps this to HTTP 400 automatically (see [13.9](#139-step-6--test-locally)).
* **Hard failure** (connectivity, SQL error): throw `ProfilingException` (optionally with `ProfilingException.LEVEL_WARN`/`LEVEL_ERROR`). Maps to HTTP 500.

Full field-by-field mapping of `ProfileColumnResult`, `ProfileBatchResponse`, and the legacy Oasis equivalents is in [Connector Interface Reference §4.4](../Connector_Interface_Reference.md#44-profilingservice-optional-contract) — use it when you need to match a specific legacy behavior (e.g. `profileStatus` semantics).

## 13.6 Step 3 — Wire it into the connector

Already done by the generator; if you're retrofitting by hand, override the default (`null`) on your connector:

```java
private final {Prefix}ProfilingService profilingService = new {Prefix}ProfilingService();

@Override
public ProfilingService getProfilingService() {
    return profilingService;
}
```

`AppsConnector.getProfilingService()` defaults to `null` — csp-api's `/v1/profiling/*` endpoints return HTTP 400 for any connector that doesn't override it, and `GET /v1/info` reports `profilingSupported: false` for it.

## 13.7 Step 4 — Declare capability in connector JSON

The generator does this for you (forcing crawler preference `P` and constraining `PROFILE_TYPES` to your mode), but if you're editing `configs/<connector>.json` by hand, match these to what you actually implemented:

```json
{
  "connectorMaster": {
    "profiling": true,
    "sampleProfiling": true
  },
  "crawlerOptions": [
    { "optionType": "CRAWLER_PREFERENCE", "optionKey": "P" },
    { "optionType": "PROFILE_OPTIONS", "optionKey": "TC" },
    { "optionType": "PROFILE_OPTIONS", "optionKey": "VC" },
    { "optionType": "PROFILE_TYPES", "optionKey": "A" },
    { "optionType": "PROFILE_TYPES", "optionKey": "S" },
    { "optionType": "PROFILE_TYPES", "optionKey": "Q" },
    { "optionType": "PROFILE_TYPES", "optionKey": "D" }
  ]
}
```

(`monetdb/src/main/resources/configs/monetdb.json` in this repo is the full DBMS reference for this block.)

`PROFILE_TYPES` allow-list by mode (enforced by the generator; match it by hand if you edit JSON directly):

| Mode | Allowed `PROFILE_TYPES` |
|---|---|
| Sample only | `S` (Sample), `D` |
| Full DBMS (JDBC) | `A` (Auto), `S`, `Q` (Query), `D` |
| Full DBMS on `FILE` kind, non-JDBC | `A`, `S`, `D` (no `Q`) |

`MR`, `QA`, `DEEP`, `RS` are not offered by the generator — don't hand-add them unless product explicitly asks for it.

**Never set `profiling`/`sampleProfiling: true` without a non-null `getProfilingService()` behind it** — [Definition of Done](10.Definition_of_Done_and_Success_Criteria.md) checks for this consistency, and it's also what real profiling jobs use.

## 13.8 Step 5 — Unit tests

The generator scaffolds `{Prefix}ProfilingServiceUnitTest.java` with one smoke test per generated method (e.g. `getRowCount_returnsZeroForStub`, `sampleProfile_returnsEmptyMapForStub`) plus, if `FILE` was selected, a `profileFile_unsupportedKind_entity_throwsUnsupported` test proving the kind guard works. It also appends `getProfilingService_returnsProfilingServiceInstance()` to `{Prefix}ConnectorUnitTest.java`.

Replace the stub assertions with real ones as you implement each method — mirror `monetdb/src/test/java/com/ovaledge/csp/tests/unit/apps/monetdb/main/MonetDBProfilingServiceTest.java` for patterns covering: row count happy path, column soft-skip (unsupported type / oversized length), sample paging/merge, and `ProfilingUnsupportedException` for disallowed kinds.

At minimum, cover:
- [ ] `getRowCount` for a supported kind returns a real (non-stub) value.
- [ ] Every overridden method calls `requireObjectKind` and rejects an unsupported kind.
- [ ] `profileColumn` soft-skip path (if implemented) sets `unsupportedDataTypeForProfile` without throwing.
- [ ] `sampleProfile` returns populated `ProfileColumnResult`s, not an empty map.
- [ ] Batch methods you didn't override still work via the inherited loop (no test needed unless you overrode them).

## 13.9 Step 6 — Test locally

Run `csp-api` as usual ([07.2](07.Development_And_Testing.md)) and either use the built-in UI's **Profiling Operations** panel (enabled automatically once `getProfilingService()` is non-null for the selected connector) or call the REST endpoints directly. All profiling endpoints are under `/v1/profiling/*`, take a JSON body with a nested `connectionConfig`, and return **HTTP 400** with `{"message": "..."}` when the operation is unsupported (`ProfilingUnsupportedException`) or **HTTP 500** on a hard failure.

| Endpoint | Body | Notes |
|---|---|---|
| `POST /v1/profiling/row-count` | `ProfileRowCountRequest` | Returns `{"rowCount": <long>}`. |
| `POST /v1/profiling/column` | `ProfileColumnRequest` (needs `fieldName`, `dataType`) | Returns `ProfileColumnResult`. |
| `POST /v1/profiling/sample` | `SampleProfileRequest` | Returns `Map<fieldName, ProfileColumnResult>`. |
| `POST /v1/profiling/file` | `FileProfileRequest` (`objectKind: "FILE"`) | Returns `FileProfileResponse`. |
| `POST /v1/profiling/batch` | `ProfileBatchRequest` (`batchMode`: `ROW_COUNT`\|`COLUMN`\|`SAMPLE`\|`BOTH`, `targets`) | Returns `ProfileBatchResponse`. |

Example — row count:

```bash
curl -s http://localhost:8800/v1/profiling/row-count \
  -H "Content-Type: application/json" \
  -d '{
    "connectionConfig": { "serverType": "monetdb", "host": "localhost", "port": 50000, "database": "demo", "username": "monetdb", "password": "monetdb" },
    "objectKind": "ENTITY",
    "containerId": "public",
    "entityId": "customers"
  }'
```

Example — column profile:

```bash
curl -s http://localhost:8800/v1/profiling/column \
  -H "Content-Type: application/json" \
  -d '{
    "connectionConfig": { "serverType": "monetdb", "host": "localhost", "port": 50000, "database": "demo", "username": "monetdb", "password": "monetdb" },
    "objectKind": "ENTITY",
    "containerId": "public",
    "entityId": "customers",
    "fieldName": "email",
    "dataType": "varchar"
  }'
```

Also check `GET /v1/info` — a connector with profiling wired up reports `"profilingSupported": true`; if it reports `false`, `getProfilingService()` is still returning `null` (see [Troubleshooting](12.SDK_Troubleshooting_Guide.md#profiling)).

## 13.10 Step 7 — Assemble, publish, ship

No extra steps beyond the normal flow — profiling code lives in the same module and is built/assembled/published the same way. Continue with [08. Assemble the new connector](08.Assemble_the_new_connector.md) and [09. Publishing the assembly JAR](09.Publishing_the_assembly_JAR.md).

Before you raise a PR, confirm the profiling-specific line item in [10. Definition of Done](10.Definition_of_Done_and_Success_Criteria.md):

> If profiling is declared (`profiling`/`sampleProfiling` true, or `P`/`PROFILE_*` crawler options): override `getProfilingService()` with a non-null `ProfilingService`, match JSON flags to the implementation, and throw `ProfilingUnsupportedException` for unsupported kinds. If profiling is not declared, leave `getProfilingService()` as the default `null` and keep those JSON flags false.
